# Fix the training loop, then rent a spot L4

The best cheap route is an **ephemeral AWS EC2 `g6.xlarge` spot instance (one NVIDIA L4) in Frankfurt**. It runs at about **$0.40/h**, sits in the lowest interruption band (<5%), is billed per second, and is created and terminated once per experiment from a new `REMOTE_BACKEND=aws` branch of the existing `REMOTE_TRAIN` hook in `loop.sh`. That hook already keeps the laptop as the only git writer. The rental is the smaller half of the answer, though. The current `model/train.py` uses only about **3–4% of the M1 GPU's paper FLOPs**: it rotates every crop single-threaded in PIL on the CPU, and it forces roughly eight GPU→CPU syncs per step. Those costs follow the code to any machine, so **shipping it unchanged buys only about 3–5×**. A 4 h M1 run becomes about 50–80 min, and an A100 or H100 would be no faster than the L4. With five training-only changes (rasters held on the GPU, `grid_sample` rotation, no per-step syncs, batch 256–512, bf16 plus `torch.compile`), the same run should drop to **minutes, about 20–50×**, for **under $0.15 per experiment**. Several of those changes also speed up the M1 and cut its heat. Make them first, measure, and then rent. One leakage hazard sits in the existing remote paths: they ship the whole `data/berlin/` folder, which includes `truedop_2024`. The new backend must upload only the three `role: train` PNGs and `meta.json`.

## The bottleneck lives in train.py, not in the M1's GPU

Published benchmarks put a base M1 about **20–30× behind an RTX 3090** on compute-bound CNNs such as ResNet-50 or VGG16. An M1 Max is roughly 8× slower than a 3090 ([MacRumors thread](https://forums.macrumors.com/threads/apple-silicon-deep-learning-performance.2319673); [tlkh/tf-metal-experiments](https://github.com/tlkh/tf-metal-experiments)), and the base M1's 8-core GPU peaks at about 2.6 TFLOPS against the RTX 4090's ~82.6 ([gpu-monkey](https://www.gpu-monkey.com/en/benchmark-apple_m1_8_core_gpu-fp32); [Notebookcheck](https://www.notebookcheck.net/M2-Pro-16-Core-GPU-vs-NVIDIA-GeForce-RTX-4090-vs-M2-8-Core-GPU_11570_11436_11375.247598.0.html)). This project does not run in that regime. `CellLocNet` has about 0.7 M parameters, four stride-2 convolutions and a 2,970-cell head, and trains at batch 64. Experiment 5's logged `train_seconds` (6,142 s over 8 epochs) works out to about **0.23 s per step, ~280 views/s, ~90 GFLOP/s**. That is a few percent of the M1's peak, so the run is overhead-bound rather than compute-bound.

Three things eat the time, measured locally on this fanless `MacBookAir10,1` on 2026-10-31. First, `extract_crop` calls `PIL.Image.rotate` once per view, single-threaded in the main process, at **0.55 ms per crop**. That comes to about **120 s per epoch (~16%)**, fully serialised with the GPU, because there is no DataLoader or prefetch. Second, each step forces about **eight host syncs** (`loss.item()`, several `.cpu()` and `int(...)` reductions, and `bool(mixed.any())` inside `cross_survey_blend`). On MPS each sync drains the GPU queue, so the next step's CPU work can never overlap the current step's GPU work ([PyTorch forum](https://discuss.pytorch.org/t/dataloader-slows-down-when-training-with-mac-mps/196185)). Third, the augmentation, blending and soft-target code launches **a few hundred tiny kernels per step**. That is the textbook overhead-bound pattern, and in it a large GPU sits mostly idle. One reported A100 loop ran at about 15% utilisation for exactly this reason ([dev.to, Alan West](https://dev.to/alanwest/why-your-pytorch-training-crawls-on-a-beefy-gpu-and-how-to-fix-it-52g8)). NVIDIA names "low utilisation, many small launches" as the best case for CUDA graphs ([NVIDIA CUDA Graph best practices](https://docs.nvidia.com/dl-cuda-graph/torch-cuda-graph/best-practices.html)). The fanless chassis probably costs extra throughput through throttling, but nobody has measured how much for an M1 Air under PyTorch ([llmconfigurator guide](https://llmconfigurator.com/en/guides/troubleshooting/macbook-thermal-throttling-llm)). Running `sudo powermetrics --samplers gpu_power` during one epoch would settle that.

The project already has one real datapoint. In July, on an earlier ACE-style model, the M1 was about **6.5× slower than an A100** on Modal, and an A10G was about 2.3× slower than the A100, so roughly 2.8× faster than the M1 (repo memory `bootstrap-status`, commit `2ac2fe9`). That fits the estimate for today's code shipped **unchanged**: a CUDA step of this shape takes about 5–15 ms, but the CPU crop floor stays at ~110–220 s per epoch, because a cloud vCPU is no faster per core than an M1 Firestorm core. That gives about **150–270 s per epoch against ~770 s on the M1, a 3–5× speed-up (±50%)**. On this code, a 4090, L4, A10G, A100 and H100 all perform about the same. Buying an A100 for it is wasted money.

## Five training-only changes unlock the order-of-magnitude gain

None of these changes touches the exported ONNX graph, so `score.py` and the size gate see the same artifact. In priority order:

1. **Keep the three training rasters on the GPU** as uint8 tensors (~426 MB) and replace per-view PIL rotation with batched `F.affine_grid` + `F.grid_sample`. This removes the CPU floor completely. GPU bilinear rotation is not bit-identical to PIL's, so log it as a semantic change.
2. **Remove the per-step syncs.** Accumulate loss, hits and confidence as device tensors and call `.item()` once per epoch, and drop the data-dependent `bool(...)` and `float(...)` branches in `cross_survey_blend`. On CUDA this alone is worth only a few percent ([HackerNoon](https://hackernoon.com/your-pytorch-model-is-slower-than-you-think-this-is-the-reason-why?source=rss)), but on MPS it is a large win, and it is a prerequisite for CUDA graphs.
3. **Raise the batch from 64 to 256–512**, with LR scaling or warm-up. This is the largest single utilisation lever. It also changes optimisation, so it is a research change and must be checked against the batch-64 score.
4. **Use `torch.autocast(bfloat16)` and `channels_last`**. The L4, A10G, 4090 and A100 support bf16. A T4 does not, so on a T4 use fp16 with a GradScaler.
5. **Apply `torch.compile`** to the model and the augmentation function. This fuses the ~45 elementwise augmentation ops, and `reduce-overhead` mode uses CUDA graphs ([NVIDIA troubleshooting](https://docs.nvidia.com/dl-cuda-graph/troubleshooting/performance-issues.html)).

An epoch is about 218k views × ~0.3 GFLOP ≈ 65 TFLOP. At a realistic 15–30% of a 4090's peak, plus the memory-bound augmentation passes, that is about **10–40 s per epoch, or ~2–6 min for 8 epochs on a 4090**. An L4 has half a 4090's bandwidth and fewer FLOPs, so expect about **5–15 min**. Both figures are order-of-magnitude estimates. The ceiling is real, though: airbench trains a small CNN to 94% on CIFAR-10 in **3.3 s on one A100** by keeping data and augmentation on the GPU ([Jordan 2024](https://arxiv.org/html/2404.00498v2)). The first remote run should log steps per second for both the unchanged and the optimised code, because no benchmark for this model on NVIDIA hardware exists.

There are two consequences for the loop. Changes 1 and 2 also help the M1, so they shorten local runs and cut the hours of sustained GPU heat even before any rental. And once training takes minutes, the fixed costs per experiment dominate: about 6 min of design and implementation agents (`timings.json`: design 289 s, implement 51 s), a few minutes of instance boot, and the figure agent now that `DRAW_FIGURES=1` is the default. That figure phase was the most expensive non-training phase when it was last timed (~15–20 min, per `CLAUDE.md`). After the code fix, the figure agent may become the longest step in each experiment.

AWS wins on several counts. The account already exists. The L4 is an Ada-generation card with bf16, enough for this model. Frankfurt rates `g6.xlarge` spot at **<5% interruption**, while the T4 sits at 15–20%. EC2 bills Linux per second with a 60-second minimum ([EC2 on-demand pricing](https://aws.amazon.com/ec2/pricing/on-demand/)). Keeping ~310 MB in S3 costs about $0.01/month, and the pull into an instance in the same region is free ([S3 price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/eu-central-1/index.csv)). The current PyTorch 2.14 Deep Learning AMI supports G6, can be resolved by a public SSM parameter, and mounts the instance's 250 GB NVMe at `/opt/dlami/nvme`. It no longer ships onnxruntime, so the export step must install it ([DLAMI 2.14 notes](https://docs.aws.amazon.com/dlami/latest/devguide/aws-deep-learning-ami-gpupt214oss-ul2604-2026-10-26.html)).

RunPod Community is cheaper per hour on paper. The July failure was not about price: it was **three days of two-writer git divergence on a persistent pod**. The stateless `remote_train.sh` written afterwards fixes that by construction, and the same create-run-terminate pattern on AWS inherits the fix. The cheapest Community 4090 was out of stock on the day of this research, though, and the in-stock Secure 4090 at $0.89/h costs more than an AWS spot L4. A 4090 is not meaningfully faster than an L4 on the unchanged code anyway. SageMaker adds a 40% markup to get the "can't be left running" guarantee, and three EC2 safety layers give the same guarantee for free (see the next steps). Kaggle is free and fully scriptable, but its ~30 GPU-hours a week cover only about a day of the loop.

One correction to the brief: Modal's credits were "used up" in July, but the Starter plan **refills $30 every month** ([Modal pricing](https://modal.com/pricing)). The working `infra/modal_app.py` harness can therefore bridge the days spent waiting for AWS quota. Its data volume must be rebuilt first (see the leakage section below).

## A remote experiment costs cents; idle time is the real risk

Approximate training-phase cost per experiment, including ~5 min of boot and S3 sync, for a run that takes ~1.7 h on the M1 (experiments 4 and 5) or ~4 h (the slow end):

| Instance | Unchanged code, 1.7 h-class (~30–45 min) | Unchanged code, 4 h-class (~55–85 min) | Optimised (~10–20 min) |
|---|---|---|---|
| `g6.xlarge` spot (~$0.40/h) | ~$0.20–0.30 | ~$0.37–0.57 | ~$0.07–0.13 |
| `g4dn.xlarge` spot (~$0.25/h) | ~$0.13–0.19 (T4 likely slower) | ~$0.23–0.35 | ~$0.05–0.10 |
| `g6.xlarge` on-demand ($1.006/h) | ~$0.50–0.75 | ~$0.92–1.43 | ~$0.17–0.34 |

A day of 10 optimised experiments therefore costs about **$1–2 on spot**, plus 19% German VAT if AWS charges it to a private account. The figures are arithmetic on the sourced hourly prices and the estimated runtimes, so they inherit the ±50% uncertainty of the speed-up estimate. The real price risk is idle time: a forgotten instance at $1/h costs more in a weekend than a month of experiments. Several cheap guards cover it. Launch with `--instance-initiated-shutdown-behavior terminate`. Put `shutdown -h +<max>` first in user-data. Add a bash `trap` in the launcher that calls `terminate-instances`. Run a tagged-instance sweep at each loop iteration. Set a free AWS Budget alert at about $30/month ([AWS Budgets pricing](https://aws.amazon.com/aws-cost-management/aws-budgets/pricing/)). A spot interruption arrives with a two-minute warning ([SageMaker spot docs](https://docs.aws.amazon.com/sagemaker/latest/dg/model-managed-spot-training.html)), and a failed train already scores 1e9 and reverts in `loop.sh`, so the harness only needs to retry once (or fall back to on-demand) instead of recording a false revert.

The AWS account has one hurdle. Every G-family quota starts at **0 vCPUs**, and a spot quota does not cover on-demand launches ([re:Post](https://repost.aws/questions/QUSPetOgBLTQuxHpy_ffhiAg/instance-launch-failed)). Both requests (`L-3819A6DF` for spot, `L-DB2E81BA` for on-demand, 8 vCPUs each, in `eu-central-1`) can be filed from the CLI without a support plan. Turnaround runs from minutes to a few days, and new accounts do get denied occasionally ([RONIN](https://blog.ronin.cloud/how-to-request-an-ec2-quota-increase-on-aws-and-get-it-approved-faster/); [re:Post](https://repost.aws/questions/QUlTBTbSCeRuC6-5HxxHvn4w/ec2-instance-creation-vcpu-limit-issue)). Accounts opened after 15 July 2025 get up to $200 in credits, but no AWS page confirms they can be spent on G instances, and a Free-plan account may first need upgrading to Paid ([AWS Free Tier FAQs](https://aws.amazon.com/free/free-tier-faqs/)).

## The held-out photograph must not be in the upload

`data/berlin/` holds 1.1 GB, but most of it is the eval capture and files training never reads. The training contract reads only `buckets(meta, "train")`, which means `relight/bb_dop20.png`, `truedop_2022.png` and `truedop_2023.png` (about 308 MB together) plus `meta.json`. Both existing remote paths ship more than that. `infra/remote_train.sh` assumes `data/` was rsynced to the pod wholesale, and `infra/modal_app.py` documents `modal volume put lowlight-data data/<area>`. Either would put `captures/truedop_2024.tif` and `relight/truedop_2024.png` on the training machine. The era's rule ("nothing under `model/` may open the eval capture") then holds only as a code convention, not physically. The AWS uploader should sync an explicit allow-list built from `meta.json`'s `role: train` entries, and it should refuse to run if any path contains the eval capture's name. Any revived Modal volume should be rebuilt the same way. Nothing in this design touches Google imagery. Scoring stays local on the laptop, and the remote returns only `models/*.onnx` and `train_info.json`.

## Conclusion

Renting a GPU is not what makes this project fast. Training is slow because of how `train.py` feeds the GPU: single-threaded PIL rotation and a host sync every few kernels. Those costs follow the code to any machine, which is why the July Modal A10G managed under 3× over the M1. Fixing the pipeline is a few dozen lines of training-only code. It makes the M1 faster and cooler on its own, and it turns a $0.40/h L4 into a minutes-per-experiment machine, where the A100 headline speed-up from the benchmarks finally becomes reachable on cheap hardware. After that, each experiment is limited by agent and figure time rather than training, so the next bottleneck to look at is the loop's own thinking time.

The order matters too. Fix the code, measure it locally, then add the AWS backend with a train-only upload allow-list. That way every remote run is cheap, fast and physically unable to see `truedop_2024`. The current remote paths, which ship the whole data folder, do not guarantee that last point.
